Descripción de la Persistencia de Datos

Proyecto eMeet · Arquitectura de Microservicios · Junio 2026

1. Visión General

eMeet implementa persistencia mediante dos tecnologías complementarias: PostgreSQL gestionado por Supabase como base de datos relacional principal, y Redis como almacenamiento en memoria para caché y motor de recomendaciones. El acceso a PostgreSQL se realiza exclusivamente a través del ORM Prisma, garantizando tipado estático, migraciones versionadas y operaciones seguras.

Stack de persistencia: Prisma 5 (ORM) → Supabase PostgreSQL (datos relacionales) + Supabase Storage (archivos binarios) + Redis (caché y recomendaciones)

2. ORM: Prisma

Prisma actúa como capa de abstracción entre los microservicios y la base de datos. El esquema centralizado se encuentra en el paquete compartido @emeet/db, lo que garantiza consistencia en todos los servicios.

2.1 Configuración del datasource

// packages/db/prisma/schema.prisma
datasource db {
  provider  = "postgresql"
  // Runtime: pooler Supabase (puerto 6543, alta concurrencia)
  url       = env("DATABASE_URL")
  // Migraciones: conexión directa (puerto 5432)
  directUrl = env("DIRECT_URL")
  schemas   = ["public", "auth"]
}

Se usan dos conexiones distintas para optimizar:

  • DATABASE_URL (puerto 6543): conexión vía PgBouncer (pooler) para las peticiones de producción. Soporta alta concurrencia con menor consumo de conexiones.
  • DIRECT_URL (puerto 5432): conexión directa usada por Prisma Migrate para aplicar migraciones sin overhead del pooler.

2.2 Multi-schema

El esquema de Prisma utiliza la feature multiSchema para acceder tanto al esquema public (datos de la aplicación) como al esquema auth (gestionado por Supabase Auth). Esto permite relaciones entre tablas de ambos esquemas.

3.1 Entidades principales

model Profile {
  id        String          @id @db.Uuid
  name      String          @default("")
  bio       String          @default("")
  avatarUrl String?         @map("avatar_url")
  location  String          @default("")
  interests EventCategory[]          // Array de enums
  createdAt DateTime        @default(now()) @map("created_at")

  authUser        AuthUser         @relation(fields: [id], references: [id], onDelete: Cascade)
  userEvents      UserEvent[]
  locatarioEvents LocatarioEvent[]
  @@schema("public")
}

model LocatarioEvent {
  id              String        @id @default(uuid()) @db.Uuid
  title           String
  category        EventCategory
  eventDate       DateTime      @map("event_date")
  lat             Float?
  lng             Float?
  imageUrl        String?       @map("image_url")
  videoUrl        String?       @map("video_url")
  creator         Profile       @relation(fields: [creatorId], references: [id], onDelete: Cascade)
  @@schema("public")
}

model UserEvent {
  // Constraint de unicidad: un usuario no puede dar like/save dos veces al mismo evento
  @@unique([userId, eventId, action], name: "user_events_user_event_action_key")
  @@schema("public")
}

4. Comandos de Migración

# Generar cliente Prisma
npx prisma generate

# Aplicar cambios al schema sin migración (desarrollo)
npx prisma db push

# Crear y aplicar migración versionada (producción)
npx prisma migrate deploy

Estos comandos se integran en el pipeline de Turborepo bajo las tareas db:generate, db:push y db:migrate:deploy.

Supabase provee tres servicios de persistencia utilizados por eMeet:

5.1 Cliente Supabase compartido

El paquete @emeet/shared expone una factory para crear clientes Supabase, evitando duplicación y garantizando configuración uniforme en todos los microservicios:

// packages/shared/src/supabase.ts
import { createClient } from '@supabase/supabase-js'

export function createSupabaseClient() {
  return createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_ANON_KEY!
  )
}

export function createSupabaseAdmin() {
  return createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_SERVICE_ROLE_KEY!  // Bypasa RLS
  )
}

5.2 Middleware de autenticación

Cada microservicio protege sus rutas mediante un middleware que verifica el JWT emitido por Supabase:

export async function requireAuth(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '')
  if (!token) return res.status(401).json({ error: 'Sin token' })

  const { data: { user }, error } = await supabase.auth.getUser(token)
  if (error || !user) return res.status(401).json({ error: 'Token inválido' })

  req.user = user
  next()
}

7. Supabase Storage: Archivos Binarios

Las imágenes y videos de eventos, así como los avatares de usuarios, se almacenan en Supabase Storage. El flujo utiliza Signed URLs para subidas seguras y directas desde el cliente sin pasar por el microservicio:

  1. El cliente solicita una Signed URL al microservicio correspondiente.
  2. El microservicio genera la URL usando el cliente admin de Supabase (con SERVICE_ROLE_KEY).
  3. El cliente sube el archivo directamente a Supabase Storage usando la URL firmada.
  4. El microservicio guarda la URL pública del archivo en PostgreSQL.

8. Integridad Referencial y Seguridad

  • Cascades: al eliminar un perfil, se eliminan en cascada sus eventos, likes, membresías y mensajes.
  • Constraints de unicidad: user_events tiene un índice único en (user_id, event_id, action) para evitar duplicados.
  • UUIDs: todas las claves primarias usan UUID v4 (@db.Uuid), compatible con Supabase Auth.
  • Row-Level Security (RLS): Supabase habilita RLS por defecto; el cliente admin (SERVICE_ROLE_KEY) lo bypasa para operaciones de servidor.
  • Variables de entorno: ninguna credencial está hardcodeada; se gestionan mediante .env.local y vercel env en producción.

9. Limpieza Automática de Datos

El microservicio app-events expone el endpoint GET /events/cleanup protegido por un CRON_SECRET. Este endpoint es invocado diariamente por Vercel Cron Jobs y elimina todos los eventos cuya fecha (event_date) sea anterior a la fecha actual, manteniendo la base de datos libre de eventos expirados.
